A .zasset is a folder holding metadata, geometry, materials, textures, thumbnails and dependencies; the folder itself is the complete asset.

Directory layout

MyAsset.zasset/
├── meta.json                 # metadata
├── node.ma / node.mb / node.fbx / node.obj / node.usd
├── node.zmetal               # material node network (material / model assets)
├── node.zlight               # light preset (light assets)
├── node.mcm                  # material → model mapping
├── textures/                 # material and light textures
├── deps/                     # collected linked files (optional; associated/ in older versions)
│   ├── textures/  caches/  proxies/  volumes/
│   ├── references/  audio/  movies/  imageplanes/  others/
├── thumb.sicon               # static thumbnail
├── thumb.aicon / thumb.mp4   # animated or video thumbnail
├── lods.json                 # current LOD index (lod0 = root geometry)
├── lod1/                     # LOD1 and later geometry
├── variants.json             # variant registry (variant geometry / thumbnails, legacy versions and version materials)
├── variants/                 # variant geometry (<id>.ma flat; older layout <version>/lod*/)
└── V1/ V2/ …                 # new versions: each a self-contained version asset (registered in meta.json)

Key files

FilePurpose
meta.jsonAsset identity and index: id, name, name_cn, tags, category, asset_type, formats, ani and so on
node.<ext>Root geometry, equivalent to lod0; several formats can coexist
node.zmetal / node.zlightMaterial or light node network, rebuilt on import
node.mcmVertex / face / edge counts and per-face material assignments, used to match models on import
textures/Textures stored flat; same name and content keeps one copy, same name with different content gets a number appended
deps/Copied only when "collect linked files" is checked; sub-directories classify by file type (the older name associated/ is still read)
lods.jsonCurrent LOD index: default_lod and the lods list; lod0 points at the root geometry
variants.jsonRegistry for variants and legacy versions: variants[] (geometry and thumbnail entries per variant) and versions[] (legacy version labels, LOD lists, per-version material paths)
variants/Variant geometry: the new layout is flat variants/<variant id>.ma (with several LODs variants/<id>_lod1.ma); the older layout is variants/<version>/lod*/; variant thumbnails also live here
V1/, V2/Embedded self-contained versions created by Update asset → Create new version, each with its own meta.json; the main asset's version_assets registers these sub-versions

The dependency ledger in metadata

Whether or not collection is checked, export scans dependencies and records the result in meta.json: dependencies_missing lists files that could not be found, dependencies_out_of_scope lists dependencies not packaged this time, and dependencies_unresolved_tokens lists unparsable tokens in paths. texture_map records the mapping from original texture paths to in-package paths, which import uses to remap them.

Two indexes: lods.json and variants.json coexist

lods.json and variants.json are two indexes used together, each covering one area, rather than "the new structure replacing the old":

  • lods.json covers the current LODs: default_lod plus the lods list, with lod0 pointing at the root geometry and lod1/… holding progressively lower detail.
  • variants.json covers variants and legacy versions:
    • Variants: one entry per variant in variants[], geometry stored flat as variants/<id>.ma (or variants/<id>/lod*/ in the older structure), thumbnails also under variants/;
    • Legacy versions: versions[] records the version id, label and LOD list, with geometry in variants/<version>/lod*/; per-version materials for those versions are exported to variants/<version>/node.zmetal and written into that version's material field.
  • These are still being written today: adding and removing variants (add_variant / add_variant_lod / remove_variant in core/zasset_builder.py) and per-version materials (_export_variant_material in core/export_orchestrator.py) all update variants.json. So finding a variants.json in an asset is not legacy residue — it means the asset uses variants or legacy versions.
  • Update asset → Create new version takes a different path: it creates an embedded self-contained V{n}/ inside the main asset and registers it in the main asset's meta.json under version_assets; this path does not write variants.json.
  • variant_types in meta.json records which internal structures the asset has (variant / lod); on the read side core/asset_scope.py merges embedded V{n}/, legacy variants/<version>/ and sibling child .zasset forms into one view, so older assets need no manual migration.
