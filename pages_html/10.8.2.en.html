After a Maya crash the port often still shows LISTENING, but that is usually a leftover process or the crash reporter; run a health check first and then decide whether to clean up or relaunch.

Symptoms

  • The Maya window is gone, or clients still cannot connect after a restart.
  • netstat shows the port listening, yet --ping is refused or times out.
  • A freshly started Maya runs on 7110 instead of the default 7001.
  • A new MayaCrashLog<date>.<time>.dmp appears in %TEMP%.

Steps

  1. Look at the Maya window first: for a crash-recovery or unsaved-changes dialog, dismissing it can rescue the unsaved scene, so do not rush to kill the process.
  2. Run python maya_bridge.py --doctor to see each port's listening, answering, PID and verdict.
  3. Once it is confirmed to be "listening but not answering", run python maya_bridge.py --doctor --kill-hung, which clears only hung instances and leaves healthy ones alone.
  4. With no usable instance run python maya_bridge.py --doctor --launch, which starts Maya and waits until it really answers.
  5. Finish by confirming the online versions and scenes with --scan / --ping; to pin a client to one port set SQUIRREL_MAYA_PORT=7110.
  6. Decide from the leftover render processes listed by --doctor (mayabatch / Render / kick / oiiotool) whether any must be ended.

Verify the result

--ping returns version | scene, --doctor marks the target port healthy, and no new crash dumps appear.

Tips and warnings

  • There is no resident supervisor process, so Maya is not started automatically when nobody is running a task.
  • --retry-if-crashed only works for idempotent or read-only tasks; a task declaring SQ_DESTRUCTIVE = True is refused.
  • Auto-save only protects scenes already saved to disk, and whether it flushes under programmatic control without human interaction is unverified, so save important scenes by hand first.
