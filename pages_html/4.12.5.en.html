The plug-in puts a read-write lock ("many readers share, a writer is exclusive, writers win") on the asset library manager, so the Maya interface and the AI / connector cannot corrupt the index by writing at the same time.

How the lock behaves

ScenarioBehavior
Read-only queries (listing, search, reading favorites)Several readers run in parallel
Write operations (loading a library, create / update / delete, writing favorites)Exclusive; while a writer waits, new readers queue (writers win)
Read lock wait limit20 seconds by default, adjustable with the SQUIRREL_LIBRARY_READ_TIMEOUT environment variable
Read wait timeoutRaises LockTimeout; the caller should report "library is busy, please retry later"
ReentrancyReads and writes reenter within the same thread; a read lock cannot be upgraded to a write lock, and upgrading raises an error

When the library is busy

  1. Stop the current large batch import, export or index rebuild.
  2. Wait for the current write to finish and retry the query or command.
  3. If it still times out, check the Script Editor and the logs for a long-running job.
  4. Do not "bypass" the lock by restarting the plug-in or editing library files by hand.

Verify the result

  • After the write finishes, queries and search work normally without LockTimeout or "library is busy".
  • The asset and category counts in the health check stay stable and nothing was lost to concurrency.

Tips

  • Write locks have no timeout by default, so long AI jobs cannot make interface writes fail; only read locks have a wait limit.
  • The lock is a runtime patch on the manager class, shared by the interface and the AI, so there is no false sense of safety limited to AI.
  • The lock only works inside one plug-in process; multiple processes or machines writing the same library have no cross-process coordination, so concurrent writes must be avoided by people.
  • Developers can use coverage_report() to check whether a public method escapes the locking scope.
