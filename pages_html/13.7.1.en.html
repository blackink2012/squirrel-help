A port showing LISTENING in netstat does not mean Maya is alive; liveness must be proven by actually dispatching a command and seeing whether it answers.

Symptoms

  • The tool reports a failed connection or timeout, yet netstat still shows the port listening.
  • --ping returns no version or scene, or the connection is refused (WinError 10061).
  • The Maya window appears open but the UI does not respond, or a dialog is in front of it.
  • A newly started Maya did not take the default port, and the client keeps reporting that it cannot connect.

Possible causes

CauseHow to tellAction
The Maya main thread is hungThe process exists and the port listens, but commands time out or are refusedConfirm, then clean the hung instance
A modal dialog blocks the main threadThe Maya window shows crash recovery, an error or an unsaved-changes promptDismiss the dialog, then retry
The crash reporter still holds the portAfter a crash the port still listens but never answersFollow the crash recovery flow
The port moved to the fallback rangeThe default port is taken by an instance of the same versionScan the fallback range 7110–7129
The client only knows a fixed portThe actual instance is on a fallback portUse auto-discovery, or set the port environment variable
Another process owns the portThe port owner is not MayaChange ports, or end the owning process

Steps

  1. Look at the Maya window first; if a modal dialog is present, dismiss it and probe again.
  2. Run python maya_bridge.py --doctor and check listening, responsive and verdict for each port.
  3. Run python maya_bridge.py --ping to confirm which Maya and which scene answer.
  4. Run python maya_bridge.py --scan to see whether the instance landed in the fallback range 7110–7129.
  5. Once you confirm it is hung and not a modal dialog, run python maya_bridge.py --doctor --kill-hung; it only cleans instances that listen but do not answer.
  6. When no instance is available, run python maya_bridge.py --doctor --launch and wait until it really answers.
  7. If the client must use a fixed port, set SQUIRREL_MAYA_PORT to the actual port.

Verify the result

--ping returns "Maya version | current scene", --doctor shows verdict=healthy for that port, and commands round-trip normally.

If it still fails

  • Check the latest port assignments in ~\.squirrel_asset_manager\bridge_port.log to see whether it keeps falling back.
  • Look in %TEMP% for a new MayaCrashLog*.dmp to tell a hang from an actual crash.
  • Never kill a process based on netstat alone; healthy instances and the user's work must stay untouched.
  • Continue with 6.7.2 "Three steps to recover after a crash", or collect information per 6.8.2 "Diagnostic workflow".
