Maya exiting during rendering is usually not Maya's own fault: the renderer core crashed and took Maya with it.

Symptoms

  • The Maya process disappears once rendering starts, with no chance for the interface to report an error.
  • The Windows event log names the renderer's own dll as the faulty module, for example redshift-core-vc140.dll or vray_*.dll.
  • The same error offset repeats and a matching MayaCrashLog*.dmp exists in %TEMP%.
  • After the crash the port is often still held by the crash reporter, appearing as "online but not answering".

Causes

  • The known Redshift path: cmds.render ends up in rsRender -render, which is asynchronous without -blk; a second render in the same Maya process collides with the cleanup of the previous one and crashes in redshift-core-vc140.dll (0xc0000005, offset 0xf77c1f).
  • Version defects in the renderer itself or GPU driver problems can also crash inside the renderer dll.

Fixes

  1. Use the plug-in's blocking channel rsRender -render -blk for Redshift thumbnails and grab the Render View, never falling back to cmds.render.
  2. For complete isolation use out-of-process Render.exe: Redshift and V-Ray must use it in mayapy standalone too, because standalone cmds.render ignores the current renderer.
  3. Never run several in-process Redshift renders in a row in one session; use headless batch rendering for bulk work.
  4. Do not hot-reload plug-in modules before rendering; doing so has reproduced the same-signature crash.
  5. After a crash, clean up leftover processes and ports as described in "Recovering after a crash", then reload the scene.

Verify the result

Repeated renders no longer crash, no new same-signature dumps appear in %TEMP%, and the event log stops showing the same module and offset.

If it still fails

Record the faulty module, exception code and offset from the event log plus the newest dump path, and report them with the renderer version; switch to out-of-process Render.exe to keep producing images meanwhile.
