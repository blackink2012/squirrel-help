When several sessions of the same version run, or Maya restarts quickly after a crash, Maya falls back from the default port to the backup range 7110~7129, and clients probe that range as well.

Why the port changes

The startup block tries this version's default port first. When that port is already taken by another instance of the same version (Maya reports 10048), it tries 7110~7129 in turn and writes the result into ~/.squirrel_asset_manager/bridge_port.log.

The client's candidate order is: the preferred year (2026) → older years → newer years → the backup range. So instances on the backup range are discovered automatically too.

Steps

  1. Run python maya_bridge.py --scan to see which candidate ports are online.
  2. To connect by version use python maya_bridge.py --maya 2025, which probes the default port and the backup range one by one and confirms identity from the year in the ping reply.
  3. When the exact port is known use python maya_bridge.py --port 7110 --ping.
  4. To pin the client to one port set SQUIRREL_MAYA_PORT=7110.
  5. To investigate past port changes read ~/.squirrel_asset_manager/bridge_port.log.

Verify the result

--ping returns version | scene; --doctor lists listening, answering, PID and verdict per port.

Tips and warnings

  • A netstat LISTENING state does not prove Maya is alive: a hung instance or a crash reporter process can hold the port. The verdict must come from actually sending a command and seeing whether it answers.
  • The probe must be a normal expression (such as ping), never print; commandPort returns the value of the expression, so print gives the caller None and misjudges a healthy instance as hung.
