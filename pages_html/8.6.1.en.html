The asset index encodes asset metadata and thumbnails into vectors ahead of time, so a search only encodes the query once and compares similarity instead of calling a large model every time.

Three kinds of index

IndexContentsDefault locationPurpose
Text semantic indexName, display name, tags, category, notes, description and so on<asset library>\.squirrel_ai_index\<official / ollama>\Searching assets with colloquial Chinese
Image vector indexImage vectors of thumbnails (encoded by the sidecar)img\ in the same directorySearch by image
Media vector indexAudio / video vectorsmedia\ in the same directoryText-to-music, recorded-audio-to-music, video-to-video

The index is split by backend: official-pipeline and Ollama vectors are not in the same space, so each backend uses its own sub-directory (official\ / ollama\). Switching backends reads the matching copy, so they never mark each other stale or overwrite each other's rebuilds.

With ai_asset_index_dir set, indexes move under that root in sub-directories split by "library + backend": text <root>\<library id>-<official|ollama>, images <root>\<library id>-<official|ollama>\img.

Key design points

  • The primary key is the library-relative path, not the asset UUID. UUIDs change between caches, live libraries and indexes, and using them silently mismatches.
  • Every record carries a signature and a text digest, so only changed rows are re-embedded; additions, edits and deletions never require a full rebuild.
  • The index records its library and model; a mismatch marks it unavailable with a rebuild command instead of returning wrong results.

What it is not

The index is derived data and contains no asset files; deleting it never damages assets and only makes the next search encode again. The index travels with the library, but when several people share a library put the index on each machine's local disk so concurrent writes from the same backend do not wait on each other.

Automatic maintenance

Opening or switching a library warms up its index in the background, and searches sync incrementally first. Building the index the first time is slower; afterwards usually only changed rows are processed.
