按「现象 → 脚本编辑器 → 专项状态 → 桥接体检 → 崩溃取证」的顺序排查，先确定问题在哪一层，再深入。

症状

  • 问题表现模糊，不知道是界面、资产库、AI、桥接还是渲染器。
  • 同一现象可能由多个原因造成，逐个试错成本高。
  • 需要给维护者提供信息，但不知道应该先收集什么。

可能原因

原因判断方法处理
没有先看完整报错只看到界面提示先复现并抓 traceback
排查顺序跳跃一会儿重装、一会儿重建索引按层排查，每层只做一个判断
状态接口没用上不知道库/索引/AI 的当前状态先查专项状态
桥接与 Maya 状态混淆分不清 Maya 卡死还是客户端问题用 --doctor 和 --ping 判活
崩溃证据没保留日志和转储被覆盖复现后立即复制

解决步骤

  1. 记录现象：发生时间、正在做什么、能否稳定复现、影响范围。
  2. 打开脚本编辑器，清空后复现一次，复制完整 traceback 的首尾。
  3. 按问题类型查专项状态：资产库用 library_health 的 op=status；搜索与 AI 用 asset_semantic_status；AI 依赖用设置里的依赖检查。
  4. 涉及 Maya 连接、卡死或断连时，运行 python maya_bridge.py --doctor，再用 --ping 与 --scan 确认实例和端口。
  5. 涉及崩溃时，记录 Windows 事件日志中的模块名与偏移，保留 %TEMP%\MayaCrashLog*.dmp。
  6. 涉及渲染时，确认是否崩在渲染器 DLL；按 6.7.3「渲染器崩溃」判断是否需要进程外渲染。
  7. 仍然无法定位时，按 6.8.3「反馈模板」整理信息后提交。

结果验证

能明确说出失败发生在哪一层（界面、资产库、索引、桥接、渲染器或授权），并拿到对应日志或状态返回。

仍不行怎么办

  • 做最小复现：空场景、单个资产、单个操作，排除场景与批量因素。
  • 保留复现前后的日志副本，不要只留最后一次启动的记录。
  • 不确定日志位置时按 6.8.1「日志位置」逐项查找。
  • 提交时附上已尝试的步骤，避免维护者重复排查。
