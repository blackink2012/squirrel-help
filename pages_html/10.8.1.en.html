When the Maya main thread is held by a command that never returns, the interface shows "not responding" and the bridge waits forever for a result; this is usually not a connection problem.

Symptoms

  • The Maya window shows Not Responding and process CPU is near 0%, meaning it waits rather than computes.
  • --ping connects to the port but does not reply, or commands time out.
  • The backend health check shows in_flight.wedged = true with the current command not returned and no modal dialog present.

Causes

  • A slow operation runs synchronously on the main thread: launching a front end, cleaning sessions, a long render or repeated sleep.
  • QApplication.processEvents() is called nested on the Maya main thread, causing event reentrancy and mutual waiting.
  • The command itself never returns, and the bridge only replies once it does.

Fixes

  1. Check the Maya window for a modal dialog first; dismiss it and retry a read-only query.
  2. Never rerun a destructive command because of one timeout; check late results first to see whether it already finished.
  3. Use python maya_bridge.py --doctor to distinguish a real hang from a dialog blocking the thread.
  4. Only after confirming a hang with no other option decide whether to force-kill Maya; unsaved scenes are lost.
  5. Prevention: run long jobs as async work, report progress(...) inside loops and check if cancelled(): break; never write your own processEvents() loop on the main thread.

If it still fails

After force-killing Maya, relaunch as described in "Recovering after a crash". Auto-save only protects scenes that were already saved, and flush-to-disk has not been observed under programmatic control, so never treat it as the only safety net.
